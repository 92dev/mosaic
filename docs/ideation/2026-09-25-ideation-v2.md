## 3. Intake (replaces triage) — evidence before any vehicle

`rule://intake` (≤ 40 lines), the invariant:
- Every external request is investigated read-only first. A verdict names `reading`, `implemented: yes|partial|no` with code citations, `touches` (paths), `risk` with reason, `retest` (human gesture), blocking `questions` only.
- Risk criteria are observable: LOW = touches known, single member repo, no contract/schema/auth/data change, reversible, covered by a targeted test; MEDIUM = any of those unknown or a behavior change callers can see; HIGH = contract/auth/data/deploy; UNKNOWN when `touches` is unknown. Unknown ⇒ never LOW.
- The orchestrator settles risk after ASSESS, REFUTE and the registry sweep. A final LOW requires a *completed* cross-family REFUTE of the same source snapshot and code revision; a missing, failed or stale REFUTE cannot authorize unattended action. Risk is re-gated on the actual per-item diff before landing; a later "safer" ruling cannot bypass the gate.
- Dispositions: `inline` / `light` / `plan` (the existing vehicles), `recommend-close` (false, stale, duplicate — with evidence; the harness never closes the request), `held` (owner, blocking question, resume condition, revisit at next intake without re-asking unchanged questions).
- One profile for now. Additive checks may be attached per request kind later; no profile can lower settled risk, remove reviewers from real implementation, or change Inline eligibility.
- Invalidation: a verdict is bound to a content fingerprint of the request (title, body, comment ids + hashes, attachments) and per-repo code revisions of its `touches`; any human change or code movement in scope re-investigates; the harness's own comment receipts do not invalidate; unknown scope ⇒ re-investigate.

`skill://intake` (≤ 80 lines): harvest via the tracker adapter (issue + comments + attachments, fingerprint recorded) → `ticket-investigator` ASSESS per item in parallel → REFUTE where required → settle → `registry-scout` sweep → write back (comment: verdict, evidence pointers, retest; labels/state per the adapter table) → route each item through `plan-triage`. Light-path sequence is explicit everywhere it is described: isolate (worktree) → implement → verify → **commit** → review the exact `base..head` (untracked files included) → repair and re-review → land the reviewed state. `ticket-investigator` keeps the baseline contract minus residue; reproduction protocols live in project reference files loaded on demand. Deploy and reporter retest are separate, project-specific skills; intake records only the deployed identity it observed.

## 4. Tracking plane (Linear first; others only when mapped)

Principle: the repo owns truth; the tracker owns coordination. The harness writes at lifecycle events and reads through two channels: the adapter (reconciliation reads of items it wrote) and `tracker-scout` (discovery). Tracker state is a human coordination claim, never proof of landing; collision checks are visibility, never locks.

Adapter contract (`rule://tracker`, per provider a capability table: native field / managed metadata / unsupported):
- Native (Linear): `title`, `state` (team-specific names mapped explicitly to planning/executing/review/done/abandoned/parked), `assignee` (= owner), labels (`mosaic`, area labels, `AI Agent`), `parentId`, `blocks/blockedBy/relatedTo`, `links` (plan doc, landed commits, evidence), comments (progress, verdicts), project status updates (`health`).
- Managed block (adapter-owned section of the description, delimited by markers, human text outside it preserved; anchor conflict → surface, never overwrite): `plan`, `repos`, `areas`, `branch` per repo (`gitBranchName` is read-only), `writer` (opaque session token + generation, no hostnames or local paths), `last-event`, `parked/blocked` reason and resume condition.
- Unsupported until mapped: Jira, Monday (Monday keeps ticket bodies in updates; the baseline's clock defect is why fingerprints replace timestamps).
- Write discipline: one automation writer per item at a time (writer token + generation in the block; a foreign generation ⇒ stop and report); human-owned fields are never written by the harness; every event has a stable identity, the returned comment/update id is retained, an uncertain write is reconciled by read-back before retry. No exactly-once claim.
- Write points: intent at `/plan` Phase 1 (creates the item in `planning` with `areas`); `approved`; `executing`; each landed wave (comment); `review`; `done` only after a landing receipt per target repo; `parked/blocked` on explicit park, cleared on explicit resume; intake verdicts as comments. Progress comment = commit-message shape (subject ≤ 72 chars; what/why/areas/evidence link), composed by `tools/tracker.ts` from the plan doc (fields from the doc, prose from the model).
- Never mirrored: registries, decisions, verification outputs, reviewer findings (linked, not copied); attachments and source excerpts are not copied into comments.

`tracker-scout` (`@smol`, read-only): the adapter enumerates the *complete* inventory of non-terminal `mosaic` items in the configured teams/projects (all pages) and computes path/area/repo intersections deterministically; the scout reads only the intersecting items' managed blocks and last comments and returns `key — owner — state — areas — last event — url`, or `COMPLETE, NO MATCH — searched: …`, or `INCOMPLETE/UNAVAILABLE — reason`. An old still-active intent is reported as stale (age), never dropped by an `updatedAt` window. Used by `/plan` Phase 1 (the approval brief names "X is also working on member-a/api.py under ENG-123 since Tue"), by `plan-triage` for light-path work in shared areas, and by `/intake`; a lookup's snapshot is reused across routing while valid.

## 5. Librarian — closure alignment, read-only, bounded

At `/execute` closure, after dispositions and before landing:
1. `tools/docimpact.ts` builds a **candidate** set (a superset, not proof): docs citing the plan id; architecture docs whose affinity is a touched member repo or `cross-area`; decisions cited by the plan; product docs naming touched contracts; roadmap items naming the plan; plus a scoped reference search for the changed public symbols/contracts. Unknown mapping ⇒ `CANNOT-EVALUATE` for that class, never an empty success.
2. `librarian` (`@balanced`, read-only) receives the candidate set, the bounded diff of changed public contracts, and may search for consumers; returns per doc: `amend` (the statement now false + replacement; mutable current-state prose only), `append` (a superseding D#; archives never rewritten), `repoint`, `no change` (with the negative-coverage evidence line). It never edits.
3. The orchestrator applies; the reviewer checks the doc diff with the records checklist; lint/doctor run.
4. Learnings: the Execution log's Deviations/Interpretations/Tradeoffs are surfaced verbatim **inside the sign-off brief** with a proposed keep/drop and reason each; the human approves by exception; zero candidates ⇒ no extra question; kept practices route through the records table (pitfall / process-rule proposal / nothing); a kept practice contradicting an existing rule is escalated, never overridden; open questions never become rules.
5. `/checkup` re-runs `docimpact` over the last N landed plans and the traceability checks (cited D#/G-x/P-x/plan ids resolve; docs citing archived plans point at the archived path, except frozen records).
