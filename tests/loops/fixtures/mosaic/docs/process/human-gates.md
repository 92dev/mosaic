Read when: drafting an approval request, an intake or leftovers digest, or a sign-off brief; this rule applies only to those briefs.
# Human briefs
- Name the audience before drafting; explain this change's flow and effects at their starting point.
- First sentence: the claim in ordinary words—who did what and what follows. Put identifying codes afterward, once, in parentheses, only to locate the thing.
- Use plain names; no session-invented labels, finding nicknames, or agent names. Vocabulary the human used in this session is already known; do not restate it.
- Keep plain wording exactly as true as the code; remove unsupported certainty and vague simplifications.
- Each sentence must be checkable from the previous one; add the missing relation instead of compressing it away.
- Include the triad: what was produced, what the human should inspect, and what happens after approval. Status and bookkeeping come after the claim, never first. Approval requests, leftovers digests, and sign-off briefs: the whole response is at most 40 physical lines; link or cite long evidence instead of pasting it. Intake digests for multi-item queues may add one verbatim verdict appendix after a ≤ 40-line brief, never duplicated inside it.
- Every identifier that stays visible carries its meaning in the same sentence; otherwise omit it. Do not claim authorship of work you only presented.
- State the decision needed and the implications of each remaining choice; omit phrases announcing how insightful the explanation is. Distinguish a routing confirmation from a plan approval. When a collision or coordination is pending, name the choice, its default, and the next action; never present execution over a known conflict as the default.
- If rewriting is still needed, read `rule://writing-for-the-reader`.
## Learnings at sign-off
- Use `skill://mosaic-execute` step 9 to present Execution-log learnings inside the sign-off brief.
- The human approves the keep-as proposals by exception; no separate learning question is needed.
- Route approved practices through `rule://records`; a conflict with an existing rule needs a human ruling, and an open question never becomes a rule.

| G-x | Work required when a stated condition becomes true |
| P-x | A known trap and the rule that prevents it |
| D# | A recorded decision and its reasons |
| F-x | A product flow or feature description |
| plan-adversary | Independent review of the proposed approach |
| REVISE / APPROVE | Changes required / accepted |
| `files:` | Files this task is allowed to change |

| light path | A small change executed and reviewed without a plan document |
