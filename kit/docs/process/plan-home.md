# Repository structure
{{MEMBERS}}{{MULTI_REPO}} Do not add member directories to the link repo; submodule wiring requires its own change.
A member may carry its own project documentation. Cross-repo architecture stays in the project's `docs/architecture/`; every element declares area affinity.
A fully member-specific architecture doc may move via a plan, leaving a redirect stub and an updated architecture index. Members communicate only through recorded schemas, event contracts, or APIs.{{/MULTI_REPO}}
# R1–R8
1. **R1 — Plan home.** {{MULTI_REPO}}`repo:` declares targets: exactly one member → `<member>/docs/plans/`; `link-repo` or multiple repos → link-repo [docs/plans/](../plans/README.md). Create the member directory when first needed.{{/MULTI_REPO}}{{MONOREPO}}Every plan declares `repo: link-repo` and lives in [docs/plans/](../plans/README.md), including work on one component; components are paths, not separate git repos or plan homes.{{/MONOREPO}} Active statuses live there; `done`/`abandoned` moves to its `archived/`, with ledger links repointed. Never delete plans or relocate them outside this convention. Older completed plans archive when their home is next touched; archived contents follow `rule://records`.
2. **R2 — Global numbering by eager reservation.** Before authoring, fetch the link repo; choose highest master-ledger number + 1, add a `draft` row with title, targets, and branch on `docs/NNNN-reserve`, land and push per `rule://git-flow`. The pushed row claims NNNN atomically. Rejected push → re-fetch, recompute/re-number, retry. The master ledger alone allocates numbers; do not scan branches or member repos. The close-only docless exception is in `rule://plan-triage`.
3. **R3 — {{MULTI_REPO}}Local ledgers.** Each member with plans has `docs/plans/README.md`, listing only its own plans and updated at every status flip on the plan's branch and commits. Both ledgers use one-line summaries; the plan holds detail. A docless or not-yet-authored plan's row carries its scope as the sole record; preserve it per `rule://records`. To create a local ledger: H1 `# Plans Ledger — <repo>`, one sentence linking master ledger and these rules, then the master table columns minus `Target repo`.{{/MULTI_REPO}}{{MONOREPO}}One ledger.** `docs/plans/README.md` lists every plan and updates at every status flip. No component-local ledgers or member scans are needed. Use one-line summaries; a docless or not-yet-authored row carries its scope as the sole record, preserved per `rule://records`.{{/MONOREPO}}
4. **R4 — Ledger truth.** Plan `status:` is authoritative. {{MULTI_REPO}}Member-homed master rows must match at creation (R2, before authoring) and terminal status; mid-flight sync is best-effort. {{/MULTI_REPO}}Link-homed master rows update at every flip.{{MULTI_REPO}} After a member branch lands and its hash exists, sync terminal status, hash, and archived link on link-repo `docs/NNNN-ledger-sync`, landed per `rule://git-flow`.{{/MULTI_REPO}}
5. **R5 — Path relativity.** Plan `files:` and `reads:` are relative to the home repo root. {{MULTI_REPO}}Link-homed cross-repo tasks prefix member paths (`<member>/...`) and each declares `repo:`; single-target tasks inherit frontmatter and omit it.{{/MULTI_REPO}}{{MONOREPO}}Component paths stay repo-root-relative; all tasks inherit `repo: link-repo` and omit their own `repo:`.{{/MONOREPO}} These fields and every path outside a link use repo-root paths; prose links use R8's file-relative frame. Do not mix them.
6. **R6 — Branching.** Read `rule://git-flow` to create the plan branch in every target.{{MULTI_REPO}} Cross-repo plans also branch the link repo, carrying plan, master-ledger flips, and Execution log. Member-homed plans carry plan + local ledger + code on their one member branch.{{/MULTI_REPO}}{{MONOREPO}} The one branch carries the plan, master-ledger flips, Execution log, and component code.{{/MONOREPO}}
7. **R7 — Orchestration home.** Sessions run from the project root; the active runtime's skills, agents, and hooks live there only{{MULTI_REPO}}, with no member copies. A link-repo worktree is a project root; its member worktrees go at `<member>/`.{{/MULTI_REPO}}{{MONOREPO}}. Components need no separate runtime files, git branches, or ledger scans.{{/MONOREPO}} Read `rule://verification` and `rule://git-flow` for project checks.
8. **R8 — {{MULTI_REPO}}Cross-repo doc{{/MULTI_REPO}}{{MONOREPO}}Doc{{/MONOREPO}} links.** Use file-relative markdown links. {{MULTI_REPO}}From a member plan, `../../../docs/...` reaches link-repo docs in this composed tree; standalone-member clone breakage is a known cost to revisit with submodules. Link-repo plans reach member files through their member directory. {{/MULTI_REPO}}Resolve each link from its own file.
